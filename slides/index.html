The I in LLM stands for intelligence 그럴듯하지만 틀린 AI 취약점 보고서가 유지보수자를 속이고 검증 시간을 빼앗는다는 초기 경고 Death by a thousand slops AI slop 취약점 보고가 curl 팀을 지치게 만든다는 문제 제기 The end of the curl bug-bounty 16시간 동안 7건, 1월에 20건 이상 제보됐지만 실제 취약점은 0건. 덤프까지 첨부된 보고서를 모두 검수해야 했다.
Not only cURL

생태계·플랫폼 차원의 대응을 논의할 정도로 확산된 문제다.

AI가 결과를 만드는 속도보다, 사람이 검증해야 하는 비용이 더 큰 병목이 된다.

Chapter 1 takeaway

AI를 배척하자는 이야기가 아닙니다!

AI는 정말 중요하고 강력한 도구입니다. 문제는 도구의 가능성을 넘어, 모든 것을 해결해 줄 거라는 AI 판타지에 빠지면 안된다는 점입니다.

AI는 활용해야 한다 생성 속도와 보조 능력은 이미 현업의 중요한 생산성 도구다.
부채는 누군가 치운다 AI가 만든 보안 부채와 검증 부채는 결국 사람이 확인한다.
전문성이 차이를 만든다 AI를 잘 쓰면서 자기 영역의 지식을 갖춘 사람이 문제를 해결한다.

AI를 잘 쓴다는 것은 많이 생성하는 것이 아니라
검증 가능한 결과를 만들게 하는 것이다.

Layer 1: docs/

docs/는 프로젝트의 뇌

DDD는 도메인과 용어를 잡고, SDD는 기능 명세와 제약을 고정한다.

PRD.md 목표, 사용자, MVP 범위, 이번에 만들지 않을 것을 정의한다.
ARCHITECTURE.md 모듈 경계, 데이터 흐름, 빌드·테스트 명령, 선호/금지 패턴을 정리한다.
ADR.md 과거 의사결정의 이유, 대안, tradeoff를 남겨 함부로 되돌리지 않게 한다.
UI_GUIDE.md 화면, 컴포넌트, 상호작용 기준을 정리한다. UI가 없으면 생략한다.

make-phase workflow

Phase 생성 과정

1사용자 요구사항을 받는다.
2PRD, Architecture, ADR에서 판단 기준을 확인한다.
3빠진 조건은 질문으로 채우고, 만들지 않을 범위를 분리한다.
4작업을 작은 Phase와 Step으로 나누고 Done Criteria를 쓴다.
5Verification을 정의한 뒤 실행 전에 사용자가 검토한다.

Approval and hooks

승인 절차와 안전장치

승인 전

  • Phase 내용 검토
  • 작업 범위와 Out of Scope 확인
  • Done Criteria와 Verification 확인
  • 변경 위험 검토

Hook

  • 허용되지 않은 파일 접근 검사
  • 필수 문서와 이전 Step 상태 확인
  • Build/Test 수행
  • 검증 실패 시 완료 처리 금지

이제 IntelliJ 화면에서 Hook이 실제로 어디서 막고, 무엇을 남기는지 확인한다.

Failure handling

실패하면 반복보다 상태를 먼저 본다

1state.json에서 실패 Step과 blocked 상태를 확인한다.
2Hook 실패, OpenCode 실행 실패, 검증 명령 실패를 구분한다.
3Done Criteria가 현실적인지, 문서와 phase가 충돌하는지 확인한다.
4필요하면 phase를 수정하고 다시 승인받은 뒤 재개한다.

Harness의 목적은 실패를 숨기는 데 있지 않다. 실패를 다음 판단 가능한 상태로 남기는 데 있다.

Harness는 AI를 묶는 장치가 아니라,
AI의 속도를 검증 가능한 결과로 바꾸는 실행 구조다.
